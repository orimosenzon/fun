# סשן 2026-07-13 (בוקר) — אבחון OOM ב-scan2, פקודת הגדלת זיכרון, מוסכמת שפה

## מוסכמה חדשה (נשמרה בזיכרון הגלובלי של קלוד)
בסשני השכלה: אורי כותב בעברית, קלוד עונה **תמיד באנגלית**.

## עדכון מצב מסשן שלא הוקלט
אורי דיווח שבסשן שלא תועד הגיעו למסקנה שהאינסטנס של scan2 ב-Cloud Run
**נגמר לו הזיכרון** (OOM) בזמן ריצת הקוד שלנו. שתי השלכות:

1. **ה-503 "Service is disabled" מסשן 09-07 כנראה כבר לא החסם הפעיל** —
   אם הפונקציה רצה מספיק רחוק כדי להגיע ל-OOM, ה-invocation עצמו עובד.
2. החסם הנוכחי הוא מגבלת הזיכרון: ברירת המחדל של Cloud Run היא **512MiB**,
   ומדדנו בעבר peak של ~375MB על PDF של 6 עמודים גם אחרי הרינדור העצל
   (baseline של imports ‏150–250MB + ‏11–15MB לכל עמוד מרונדר + עותקי
   base64 + tmpfs שנספר כ-RAM).

## מה הוכן (טרם בוצע — אין gcloud במחשב פרדס חנה)
פקודה להרצה ב-**Cloud Shell** (יוצרת revision חדש, שומרת secrets והגדרות):

```bash
gcloud run services update scan2 \
  --region europe-west1 \
  --project master-gecko-500709-t0 \
  --memory 2Gi
```

אימות אחרי:

```bash
gcloud run services describe scan2 \
  --region europe-west1 \
  --project master-gecko-500709-t0 \
  --format='value(spec.template.spec.containers[0].resources.limits.memory)'
```

נבחר 2Gi (ולא 1Gi): סריקות ארוכות/ברזולוציה גבוהה או שתי בקשות מקבילות
על אותו אינסטנס יכולות לחצות 1Gi; ‏CPU יחיד (ברירת מחדל) תומך עד 4Gi;
העלות שולית (חיוב לפי משך בקשה). אפשר לאמת את אבחון ה-OOM בלוגים:
`Memory limit of 512 MiB exceeded`.

## צעדים הבאים
1. **להריץ את הגדלת הזיכרון ב-Cloud Shell** + לאמת (הפקודות למעלה).
2. לבדוק ריצה אמיתית של scan2 מקצה לקצה אחרי ההגדלה.
3. להעביר את קבצי `~/scan2-src` מ-Cloud Shell לגיט (`haskala/products/scan2/`)
   — עדיין לא מגובים!
4. לעדכן את ירון על דה-דופליקציה ב-`run_workspace_scan()` (פתרון ledger
   מוכן ב-`math-checker/poller.py`).
5. פתוחים מקודם: פריסת math-checker ל-Cloud Run; ‏DNS
   (`checker.bdika.net`/`math.bdika.net`) עדיין מצביע ל-VM נטוש.
