# סשן 2026-07-13 (אחה"צ/ערב) — scan2: תוקן ה-503, נמצא באג אמיתי חדש

## מה בוצע (דרך Cloud Console, לא gcloud)
1. **הוגדל הזיכרון של scan2 ל-2 GiB** — Cloud Run → scan2 → Edit & deploy new revision →
   Containers → Settings → Memory: 512 MiB → 2 GiB → Deploy.
   revision חדש: `scan2-00018-8lf`, 100% traffic. (זה השלב שתוכנן בסשן הבוקר של היום,
   רק שבוצע ב-UI במקום ב-gcloud כי לא היה gcloud זמין).

2. **התגלה הגורם האמיתי ל-503 "Service is disabled"** — זה **לא** היה Regional Access
   Boundary ארגוני כפי שחשבנו קודם. הגורם: **Scaling היה מוגדר Manual עם 0 instances**.
   ב-Cloud Run, Manual scaling עם 0 = "disable the Service. Any traffic sent to the
   disabled Service will return an error" (כתוב במפורש בדיאלוג של גוגל). זה הסביר גם
   למה בדיקת curl ישירה נכשלה.
   **תוקן:** הוחלף ל-**Auto scaling (Min: 0, Max: 20)** — מתאים לדפוס עבודה של
   טריגר לפי דרישה (Pub/Sub push), במקום Manual שנשאר קבוע על 0.

3. **אומת מנגנון ההפעלה** — בלשונית Triggers של scan2 יש **Pub/Sub push subscription**
   על topic בשם `scanNow`. בהרשאות ה-topic מופיע `Cloud Scheduler Service Agent` —
   מאשר שיש Cloud Scheduler שמפרסם ל-topic הזה בתדירות קבועה (כמו שתואר במסמך
   הארכיטקטורה: "Scheduler (every ~5 min)").

4. **בדיקה ידנית ב-Pub/Sub** (Topic scanNow → Messages → Publish message, גוף "test"):
   - ניסיון ראשון (**לפני** תיקון ה-scaling) — "No newer entries found matching the
     current filter" בלוגים של scan2. ההודעה לא הגיעה לשירות בכלל (מתיישב עם התאוריה
     שה-Manual@0 חוסם הכול).
   - ניסיון שני (**אחרי** תיקון ה-scaling) — **עבד**. אינסטנס חדש עלה, הקוד התחיל
     לרוץ (`math-checker:[job] 1 page(s) to render at 200 DPI; model=opus auto_orient=True`).
