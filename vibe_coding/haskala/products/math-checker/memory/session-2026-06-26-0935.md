# סשן 2026-06-26 — תכנון אינטגרציה ל-Google Classroom

סשן תכנון/אסטרטגיה (לא קוד). הוגדרה הארכיטקטורה לאינטגרציה של checker עם Google Classroom,
ונכתב מסמך הסבר בגובה התמונה הגדולה לשיתוף עם השותפים.

## החלטות ארכיטקטורה שהתקבלו

1. **טריגר = polling, לא push.**
   ל-Classroom API *יש* push דרך Pub/Sub (feed מסוג `COURSE_WORK_CHANGES`), אבל הוא מסורבל:
   דורש scope ייעודי + הרשאות admin על הדומיין + חידוש registration כל שבוע, וההתראה "דקה"
   (עדיין צריך לקרוא ל-API לשלוף את ההגשה). לכן: **Cloud Scheduler** ששואל כל ~5 דק'
   "הוגש משהו חדש?". push אפשרי כשדרוג עתידי אם תידרש מהירות אמיתית.

2. **הרצה = Cloud Run, לא Cloud Functions.**
   הנימוק הישן ("לפונקציות יש הגבלת זמן") מיושן — לשתיהן 60 דק' ל-HTTP (gen2). הסיבה האמיתית:
   האפליקציה כבר Flask, ו-Cloud Run עוטף אותה כמעט as-is. הגירה **מלאה** מ-HF Space ל-Cloud Run.

3. **תור משימות = Cloud Tasks.**
   לא לבדוק בתוך ה-handler של ה-poll. ה-poller דוחף task לכל הגשה; Cloud Tasks מספק retries+backoff
   (קריטי — בסשן הקודם Opus החזיר 529 לאורך כל הסשן), deadline משלו, ואידמפוטנטיות לפי submission ID.

4. **השלכה מרכזית בקוד:** `JOBS: dict` (app.py:125) חי בזיכרון התהליך → לא שורד ב-Cloud Run עם
   מופעים מרובים + scale-to-zero + retries. חייב לעבור ל-**Firestore** (persistent store, idempotency
   לפי submission ID כ-document key). זה השינוי המבני הגדול ביותר וגם נקודת ההתחלה.
