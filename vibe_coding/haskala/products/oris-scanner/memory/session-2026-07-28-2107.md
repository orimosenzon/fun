## 1. Cloud Run mechanics — measured, not assumed

Ori asked how the service is actually triggered and what a minute-by-minute poll costs.
Everything below is measured against production, not estimated from the code.

- **Trigger chain**: Cloud Scheduler job `oris-scanner-poll` → HTTP POST (empty body,
  OIDC-signed) → Cloud Run → functions-framework/Flask → `process_my_drive_files`.
  No Pub/Sub (removed earlier; only needed for Classroom push notifications).
- **No parameters travel in the request.** The `request` argument is accepted and
  ignored outright; the POST is a doorbell. Configuration comes from three places:
  env vars (`--set-env-vars`), Secret Manager (`--set-secrets`), and Classroom itself
  (description = question, `[model: …]` tag, rubric, attachments) — the last being the
  only one a teacher can change without a deploy.
- **Idle scan: ~6.0s**, 1 vCPU / 512 MiB, request-based billing (`cpu-throttling`
  default), so nothing is billed between polls.
- **15 Classroom API calls per scan** (measured via the Monitoring API:
  450 calls / 30 min).

## 3. Polling frequency: `*/1` → `*/5`

Cost analysis (Cloud Run free tier: 2M requests, 180,000 vCPU-s, 360,000 GiB-s/month):

| | `*/1` | `*/5` |
|---|---|---|
| requests/month | 43,830 | 8,766 |
| vCPU-s/month | 262,980 | ~52,600 |
| cost | ~$2/month (CPU overage only) | **$0** |

Key finding presented to Ori: `*/15` costs exactly the same as `*/5` (both fully inside
the free tier) while tripling the wait — so `*/5` is the floor worth taking, and the
old `*/15` idea was strictly dominated. He chose `*/5`.

Caveat recorded in `setup_infra.sh`: the free tier is shared with `checker`/`scan1`/
`scan2`; if they consume it, oris-scanner costs ~$1.3/month rather than zero.

**Drift found and fixed**: the 07-23 session note claimed `setup_infra.sh`'s `SCHEDULE`
default had been changed to `* * * * *`. It had not — only the live job was updated;
the file still read `*/15` (untouched since 07-22). Lesson: when a change touches both
`gcloud` and the repo, it is easy to do only the first and document both.

## 4. Unnamed rubric attachments — content-based routing (new feature)

Problem Ori raised: a rubric attached as a plain assignment PDF was ignored, because
`resolve_rubric_material` matched on filename only (`rubric`/`רובריקה`/`מחוון`) or an
explicit `[rubric: …]` tag. Teachers do not rename files, so the feature rarely fired.

Constraint that shaped the design: a material rubric **replaces** the bundled rubric
entirely (`checker.py`), so blindly adopting any PDF would drop the score scale and
criteria whenever the attachment is an assignment brief rather than a rubric.

Ori chose content-based routing over "always treat it as a rubric". Implemented:

- `core.resolve_rubric_material` — new step 3: a **lone** Drive attachment is adopted
  as a candidate with `certain=False`. Named/tagged ones carry `certain=True`.
  Several unnamed attachments → no guess, warning explains how to disambiguate.
- `core.classify_document(text, model_key)` — new. One short text-only call
  (`max_tokens=10`), all four providers, mirroring `detect_rotation`'s shape. Returns
  `rubric` or `assignment`; **defaults to `assignment` on any doubt**, because extra
  context can only help while a wrong rubric destroys the score scale.
- `checker.load_material_rubric` — returns `kind` alongside `{name, content}`;
  `certain=True` skips classification.
- `checker.check_hw` — a document classified `assignment` is folded into the question
  and removed from the rubric slot; the bundled rubric stays.

Verified: 10 offline logic cases pass, and 5 live cases against real Gemini — including
the trap case, a "how to build a rubric" guide correctly classified as `assignment`.
