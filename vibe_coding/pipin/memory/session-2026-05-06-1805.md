- אחרי `git pull` נשארו רק שני שינויים שהיו ייחודיים לעבודה שלי, ואותם קימשתי:
  1. **תיקון POST handler** (`ce64686`): הקוד דחה כל שמירה שנייה עם `already_canonized`, מה שאומר שאחרי שמירת נרטיב, ה-`saveCanonLocation(id, null, imageUrl)` ל-image שובש בשקט. זה פגע בעולם המשותף — תמונות לא נשמרו ב-canon וכל שחקן ראה תמונה אחרת. עכשיו ה-handler ממלא רק שדות ריקים, לעולם לא דורס.
  2. **session-start git sync** (`~/.claude` commit `2f35b3f`, מקומי בלבד): שלב חדש שמריץ `git -C <project-root> pull --ff-only` לפני קריאת memory. עובד גם לפרויקטים נפרדים (golem) וגם לתת-תיקיות בתוך vibe_coding (pipin/inbal). זה תיקון בשורש ל-multi-machine drift.

## למה זה היה Guest Mode חכם
המכונה השנייה הוסיפה כפתור "כנס כאורח" שמאפשר לעבור בין מקומות שתועדו ע"י שחקנים אחרים בלי מפתח Gemini. זה בדיוק engagement loop נכון: אורחים יכולים לטעום את העולם, הופכים לשחקנים פעילים כשהם רוצים לתרום מקומות חדשים.

## הצעדים הבאים
1. **Deploy בפועל ל-Render** — לדחוף ל-GitHub כבר נדחף, עכשיו רק ליצור Blueprint ב-render.com מהריפו והוא יזהה את `render.yaml` אוטומטית. החלטה: כן/לא לשלם על persistent disk ($1/חודש) — בלי זה ה-DB מתאפס בכל redeploy. ל-MVP מספיק בלי, אבל לוודא שאת הסשן הראשון "האמיתי" עם משתמשים אמיתיים נעשה אחרי שיש disk.
2. **לתת ל-`~/.claude` remote** — שני סשנים ברצף שבהם הסנכרון נכשל בגלל שאין tracking branch. שווה להסדיר GitHub repo ל-`~/.claude` כדי שכל המכונות יסונכרנו.
3. **Stable seed ב-Pollinations URLs** — אופציונלי. בלי seed כל קריאה מקבלת תמונה אחרת; ה-canon מסתיר את זה (ה-URL הראשון נשמר), אבל אם cache בדפדפן מתאפס לפני שהשרת שמר, יקבלו תמונה שונה. שיפור קוסמטי.
4. **Real users feedback** — אחרי deploy, להזמין 2-3 חברים לשחק. לראות איך עובד shared world בפועל.
